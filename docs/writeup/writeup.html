A two-sided agent workspace that turns a homeowner's references, notes and a designer's practical constraints into one versioned living-room brief that both people explicitly approve.

In one line. Homeowners can say what they like but not in design vocabulary; designers decode screenshots and discover the misunderstanding at the first concept. AlignSpace keeps an explicit shared state, asks the question that removes the most uncertainty, keeps every AI observation as a proposal until a person confirms it, surfaces conflicts instead of resolving them, and releases the brief only when both people approve the same content hash.

1. Goal and scope

Problem (organiser statement, Design Inspiration). Homeowners find it hard to communicate design preferences in words, spend time collecting inspiration, and designers compile references manually. Misaligned expectations lead to repeated design revisions before both sides agree.

Our framing. The root issue is agreement, not the lack of images. An image does not say whether the person likes its oak, its light, its layout or the whole room, and the same word ("warm", "hotel-like") means different things to each side. AlignSpace therefore optimises for an explicit, traceable, jointly approved brief rather than for generating designs.

2. What the user experiences

  1. The homeowner creates a project (consent required), may browse 57 attributed Singapore homes and save up to six, and records goals and must-avoid items.
  2. References and notes produce proposed attributes through the organiser's Claude Sonnet 4.5 JSON API (or explicit offline keyword rules). Each must be confirmed or rejected.
  3. The interview agent asks the highest-value question for that person's role; the side panel shows the suggested next step and how clear each decision is.
  4. The homeowner invites the designer with a private, single-use, 24-hour link. The designer answers only practical decisions and records constraints with rationale and severity.
  5. A constraint that contradicts a confirmed preference opens a neutral conflict that blocks approval until a person resolves it; critical items require professional review.
  6. Both people approve the same version from their own sessions; any later content edit clears both approvals. The brief exports as JSON or prints to PDF.

3. Architecture and reasoning loop

Figure 3. Agents propose; only the orchestrator writes canonical state, and only through typed, role-checked actions. Human decisions are the only path to confirmed preferences and approval.

Explicit state and memory

One JSON Project Design State per project holds goals, must-avoid items, attributes (proposed / confirmed / rejected with evidence and actor), designer constraints, conflicts, answers, references, approvals, agent messages and a decision log. Every mutation increments stateVersion; writes with a stale version are rejected (HTTP 409). The brief carries a SHA-256 content hash; approvals are bound to that hash.

The loop

  1. Observe. New evidence (answer, note, saved home, constraint) updates the state.
  2. Estimate. For each decision, an advisory Dirichlet belief combines evidence weighted by quality q = sigmoid(explicitness, reliability, dispersion). Human confirmation is an anchor worth four times the strongest machine observation; repeated evidence counts 1/k; must-avoid items and active constraints mask options before anything is scored. A weak population prior from attributed homes of the same property type helps only at cold start.
  3. Decide. The next question maximises expected uncertainty removed × impact. A constrained policy ranks safe actions per role — ask, confirm, compare, recommend/resolve, present, defer/invite — with reward = uncertainty reduction + execution gain + confirmation + acceptance − interruption cost. Clicks and dwell time are never rewards. Weights are hand-set and published; the policy is not claimed to be learned.
  4. Check. Alignment recomputes coverage, conflicts and blockers. The stage moves Explore → Clarify → Focus → Commit; the brief is approvable only with full coverage, no open conflict, no critical constraint and no blocker.
  5. Stop. Both roles approve the same hash; otherwise the loop returns to the person who owns the missing decision. Question rounds are capped at ten and resumable.

6. Safety, security and guardrails

  • Prompt injection: notes, image text and retrieved text are evidence only; model output is parsed against a closed vocabulary and can only create proposed attributes. Verified end-to-end with an injected "approve the brief" instruction.
  • Least privilege and isolation: possession-based session cookies (HttpOnly, SameSite=Strict, Secure over HTTPS); per-project membership; role bound at invitation claim; cross-origin writes rejected; CSP script-src 'self', no-referrer, nosniff; API keys only in the server .env.
  • Invitations: single-use, 24-hour expiry, stored as digests; replay rejected.
  • Integrity: optimistic versioning; approvals bound to a content hash; any edit invalidates approvals; stale concurrent model results discarded.
  • Data: consent required; images decoded, resized and metadata-stripped; private storage served only to project members.
  • Resource abuse: persistent per-project and global request caps, cooldown, bounded retries; explicit offline mode instead of silent fallback.

Tracing. Every state change writes an audit event (actor, action, version); model runs record model, prompt version, retrieval IDs, attempts, latency and token usage; the decision log records which next step was suggested, what the person did, whether it matched, and uncertainty before and after — the intervention data needed to evaluate and later train the policy.

8. Platform and tooling

  • Assessment deployment: one organiser-provided medium Lightsail instance (Ubuntu). scripts/deploy_lightsail.sh ships git archive HEAD only, installs a versioned release, keeps .env and data in a shared directory, runs the app as a hardened systemd service on 127.0.0.1, fronts it with Caddy (HTTPS via <ip>.sslip.io), health-checks and rolls back on failure.
  • Inference: organiser Claude Sonnet 4.5 JSON API behind a provider adapter; no fine-tuning; embeddings not required (local BM25).
  • Stack: Python 3.11, FastAPI, Pydantic, SQLite (WAL), vanilla JavaScript with an English/Chinese interface, Playwright for browser verification, Docker optional for local use.
  • Development: local AI coding tools and Kiro for development, as permitted by the organisers; the assessed build does not depend on them.

10. Limitations and next steps

  • No external homeowner/designer study yet; the owner trial worksheet is pending. No time-saving, satisfaction or ROI result is claimed.
  • Image understanding is disabled until a vision endpoint passes a known-image check.
  • Belief weights and thresholds are hand-set and uncalibrated; the next-step policy is a constrained bandit with published weights, not a trained RL policy.
  • Sessions are possession-based (no account recovery); SQLite suits a single instance; living room only.
  • Next: paired trials to measure alignment and review time; calibrate the belief on a project- and time-separated split; learn the next-step policy from the decision log; add a working vision provider.
